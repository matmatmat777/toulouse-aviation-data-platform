# Toulouse Aviation Data Platform — Production Runbook

## 1. Purpose

This runbook describes the operational procedures for the Toulouse Aviation Data Platform.

It explains how to:

- monitor pipeline executions;
- diagnose failures;
- investigate data-quality incidents;
- replay failed processing;
- correlate Airflow, PySpark and quality metrics;
- handle alerts;
- manage configuration and credentials;
- recover the pipeline after an incident.

The objective is to make the pipeline observable, reproducible and recoverable.

---

## 2. Pipeline overview

The target architecture is:

```text
Aircraft API
    |
    v
Python Producer
    |
    v
Kafka
    |
    v
Kafka Consumer
    |
    v
GCS RAW
    |
    v
PySpark
    |
    +----> REJECTED / quarantine
    |
    v
PROCESSED
    |
    v
BigQuery
    |
    v
dbt
    |
    v
Analytics / Power BI
```

Airflow orchestrates the batch processing stages and their dependencies.

Kafka streaming ingestion is independent from Airflow.

## 3. Data zones

### RAW

RAW contains source data as received by the ingestion layer.

RAW data must remain immutable.

A processing failure must never be fixed by manually modifying RAW data.

If transformation logic is incorrect:

1. fix the processing code;
2. add or update automated tests;
3. replay processing from RAW.

### PROCESSED

PROCESSED contains validated and transformed records generated by PySpark.

The data can be regenerated from RAW when necessary.

### REJECTED

REJECTED contains records that fail data-quality rules.

Rejected records are preserved for:

- diagnosis;
- audit;
- debugging;
- correction of transformation rules.

## 4. Airflow DAG

Main DAG:

```text
aviation_pipeline
```

Current execution flow:

```text
start
  |
  v
get_processing_date
  |
  v
check_raw_file
  |
  v
run_pyspark
  |
  +------------------------+
  |                        |
  v                        v
check_processed_data   quality_failure_diagnostic
  |
  v
end
```

The `quality_failure_diagnostic` task is triggered when `run_pyspark` fails.

The DAG currently uses:

```text
schedule=None
```

because the repository is a local training and portfolio environment.

A production deployment could use a scheduled execution after validating the ingestion SLA and upstream data availability.

## 5. Processing date

The pipeline receives a processing date through the Airflow parameter:

```text
processing_date
```

Example:

```text
2026-09-03
```

This value identifies the logical data partition being processed.

It must not be confused with the execution timestamp.

---

## 6. Run identification

Each Airflow execution has a unique:

```text
run_id
```

Example:

```text
manual__2026-09-11T08:54:28.667357+00:00
```

The same `run_id` is propagated from Airflow to the PySpark job and persisted in quality metrics.

This allows correlation between:

```text
Airflow DagRun
      |
      v
Airflow task logs
      |
      v
PySpark logs
      |
      v
quality_metrics.json
      |
      v
alert.json
```

A retry of the same logical Airflow run keeps the same `run_id`.

The Airflow `try_number` identifies the individual execution attempt.

Therefore:

```text
run_id      = logical pipeline execution
try_number  = task execution attempt
```

## 7. Structured logging

The PySpark application logs operational information using structured key/value information.

Important fields include:

```text
run_id
processing_date
global_status
raw_count
rejected_count
rejection_rate
duplicate_rate
freshness_minutes
```

When investigating an incident, always start with the Airflow `run_id`.

This identifier should be used to correlate logs and persisted monitoring artifacts.

## 8. Data-quality controls

The PySpark pipeline evaluates several data-quality dimensions.

### Rejection rate

Percentage of RAW records rejected by validation rules.

Current thresholds:

```text
<= 5%       OK
> 5%        WARNING
> 20%       FAILED
```

### Duplicate rate

Percentage of duplicate records detected before deduplication.

Current thresholds:

```text
<= 2%       OK
> 2%        WARNING
> 10%       FAILED
```

### Volume variation

Compares observed volume with an expected volume when a reliable expected count is available.

Expected volume must come from a real SLA or trusted reference.

The pipeline must not invent an expected count merely to satisfy the control.

### Freshness

Measures the age of the data when a reliable reference time is supplied.

Current thresholds:

```text
<= 30 min       OK
> 30 min        WARNING
> 120 min       FAILED
```

A missing reference time means that freshness cannot be evaluated reliably.

---

## 9. Global quality status

Individual quality checks are aggregated into a global status.

Priority is:

```text
FAILED
  >
WARNING
  >
OK
```

Therefore, if one critical quality rule is `FAILED`, the global pipeline quality status becomes:

```text
FAILED
```

---

## 10. Quality Gate

When the global quality status is:

```text
FAILED
```

the PySpark job raises an exception.

This produces a non-zero process exit code.

Airflow consequently marks:

```text
run_pyspark = FAILED
```

This behavior is intentional.

A quality failure must not silently produce a successful pipeline execution.

Logging an error without raising an exception would allow the process to exit successfully and Airflow could incorrectly mark the task as `SUCCESS`.

---

## 11. Quality metrics

Quality metrics are persisted per pipeline execution.

Logical path:

```text
data/
└── metrics/
    └── aircraft_positions/
        └── year=YYYY/
            └── month=MM/
                └── day=DD/
                    └── run_id=<RUN_ID>/
                        └── quality_metrics.json
```

Example:

```text
data/metrics/aircraft_positions/
year=2026/
month=09/
day=03/
run_id=manual__.../
quality_metrics.json
```

Persisting metrics by `run_id` prevents one execution from overwriting the monitoring information of another execution.

## 12. Alerts

A critical quality failure generates an alert artifact.

Logical structure:

```text
data/
└── alerts/
    └── aircraft_positions/
        └── processing_date=YYYY-MM-DD/
            └── run_id=<RUN_ID>/
                └── alert.json
```

An alert contains operational information such as:

```text
run_id
processing_date
global_status
rejection_rate
duplicate_rate
freshness_minutes
message
```

The current implementation persists local JSON alert artifacts.

In a real production environment this layer could be connected to:

- Slack;
- Microsoft Teams;
- email;
- PagerDuty;
- Cloud Monitoring;
- another incident-management platform.

The repository does not claim that these external integrations are currently deployed.

## 13. Incident classification

Pipeline failures should first be classified into two categories.

### Technical failure

Examples:

```text
Python exception
Spark failure
missing file
permissions error
network error
dependency unavailable
invalid configuration
```

A technical failure may happen before quality metrics are generated.

### Data-quality failure

Examples:

```text
excessive rejected records
excessive duplicates
invalid schema
unexpected null values
invalid coordinates
invalid altitude
stale data
unexpected volume
```

A Data Quality failure normally produces `quality_metrics.json` before the Quality Gate stops the job.

---

## 14. Diagnostic procedure

When `run_pyspark` fails:

### Step 1 — identify the run

Retrieve:

```text
run_id
processing_date
try_number
```

from Airflow.

### Step 2 — inspect Airflow logs

Open the logs for:

```text
run_pyspark
```

Search for the same `run_id`.

### Step 3 — inspect quality metrics

Look for:

```text
quality_metrics.json
```

under the corresponding processing date and `run_id`.

### Step 4 — inspect alert

If:

```text
global_status = FAILED
```

inspect the corresponding:

```text
alert.json
```

### Step 5 — inspect rejected data

Analyze rejected records and their rejection reasons.

Examples:

```text
INVALID_OR_MISSING_ALTITUDE
ALTITUDE_BELOW_ZERO
```

### Step 6 — identify the root cause

Determine whether the incident is:

```text
technical
```

or:

```text
data quality
```

Do not replay the pipeline before understanding the failure when the same input would deterministically reproduce it.

---

## 15. Missing quality metrics

The Airflow diagnostic task handles the case where:

```text
quality_metrics.json
```

does not exist.

Instead of generating a second misleading failure, it reports:

```text
QUALITY METRICS : NOT AVAILABLE
```

This usually means:

```text
the PySpark job failed before metrics persistence
```

or:

```text
the metrics are inaccessible
```

The operator should then inspect the `run_pyspark` logs for a technical failure.

---

## 16. Retry versus idempotence

Retry and idempotence are different concepts.

### Retry

Retry means:

```text
execute an operation again after failure
```

### Idempotence

Idempotence means:

```text
executing the same operation multiple times
produces the same final state
```

Retries are safe only when the processing strategy prevents uncontrolled duplicate effects.

Examples of idempotent or controlled strategies include:

```text
MERGE / UPSERT
partition overwrite
deterministic deduplication
transactional writes
```

A blind append is generally unsafe when a task can be retried.

---

## 17. Recovery strategy

The pipeline should resume from the last valid persisted stage whenever possible.

Example:

```text
RAW        SUCCESS
PYSPARK    SUCCESS
BIGQUERY   FAILED
DBT        NOT_STARTED
```

Recovery should be:

```text
SKIP RAW
SKIP PYSPARK
RUN BIGQUERY
RUN DBT
```

It should not automatically restart ingestion or PySpark when their persisted outputs are already valid.

This reduces:

- unnecessary computation;
- execution time;
- duplicate risk;
- operational complexity.

---

## 18. Pipeline checkpoint

A checkpoint prototype is implemented in:

```text
spark/jobs/pipeline_state.py
```

It can persist a state such as:

```json
{
  "processing_date": "2026-09-03",
  "run_id": "recovery-test-001",
  "raw": "SUCCESS",
  "pyspark": "SUCCESS",
  "bigquery": "FAILED",
  "dbt": "NOT_STARTED"
}
```

This demonstrates recovery from the last successful stage.

The checkpoint mechanism is currently a portfolio/training implementation.

It is not fully integrated into the Airflow DAG.

Airflow already maintains task execution state, so a production design must carefully decide whether an additional external checkpoint is necessary.

Two competing sources of truth should be avoided.

---

## 19. Replay procedure

Before replaying a failed processing date:

1. identify the original `run_id`;
2. determine the failed stage;
3. verify whether previous stage outputs are valid;
4. identify and fix the root cause;
5. add or update automated tests when code changes;
6. replay only the necessary stages;
7. verify quality metrics;
8. verify downstream outputs.

Never modify RAW data to make a replay succeed.

---

## 20. Example — Data Quality incident

Initial state:

```text
check_raw_file              SUCCESS
run_pyspark                 FAILED
check_processed_data        UPSTREAM_FAILED
quality_failure_diagnostic  SUCCESS
```

Metrics:

```text
raw_count        = 10000
rejection_rate   = 28%
duplicate_rate   = 3%
global_status    = FAILED
```

Correct response:

```text
1. identify run_id
2. inspect quality metrics
3. inspect rejected records
4. identify rejection reason
5. correct transformation if necessary
6. add automated test
7. replay from immutable RAW
8. validate new quality metrics
```

Incorrect responses include:

```text
blindly retrying the same deterministic failure
modifying RAW data
deleting rejected records
raising the quality threshold only to make the pipeline pass
```

---

## 21. Example — schema evolution incident

Suppose altitude changes from:

```text
12000
```

to:

```text
"12000 ft"
```

and causes a large rejection rate.

The correct response is not to edit RAW.

The processing logic should be adapted explicitly if the new source format is valid and expected.

The change should be covered by an automated test before replaying the affected RAW partition.

## 23. Secrets and credentials

Secrets must never be committed to Git.

The project favors:

```text
Application Default Credentials
Workload Identity Federation
IAM
least-privilege service accounts
```

rather than static service-account key files.

Important distinction:

```text
Authentication
    = Who are you?

Authorization
    = What are you allowed to do?
```

A `403` error generally indicates an authorization/IAM problem rather than an authentication mechanism problem.

---

## 24. IAM principle

Each component should receive only the permissions required for its function.

Examples:

```text
GCS writer
    -> write permission only where possible

BigQuery loader
    -> required BigQuery permissions

CI/CD identity
    -> only permissions required by CI/CD
```

Production Spark processing should use a dedicated identity with appropriate read access to RAW and write access to processed/rejected zones.

---

## 25. DEV and PROD

Development and production configuration must remain separated.

Infrastructure is managed with Terraform environments.

Examples:

```text
terraform/environments/dev
terraform/environments/prod
```

Terraform remote state is also separated by environment.

Application code should remain reusable between environments.

Configuration changes should select the environment rather than requiring source-code modifications.

## 28. Runtime artifacts

Runtime monitoring and recovery artifacts should not be treated as source code.

Examples:

```text
data/metrics/
data/alerts/
data/state/
```

These files are generated by executions.

Production environments should persist operational data in durable shared storage rather than depending on a local filesystem.

Possible targets include:

```text
GCS
BigQuery
Cloud Monitoring
dedicated observability systems
```

## 29. Known limitations

The repository is an engineering portfolio and training platform, not a fully deployed production system.

Current limitations include:

- Airflow uses a local environment;
- `schedule=None` is intentional for manual demonstrations;
- alerting currently persists JSON rather than sending real notifications;
- checkpoint recovery is demonstrated but not fully integrated into Airflow;
- local metrics are not a production monitoring backend;
- BigQuery and dbt are not yet represented as complete downstream Airflow tasks in the current DAG;
- the full runtime PySpark pipeline is not executed end-to-end by CI;
- external SLA values for expected volume and freshness are not currently available;
- production Spark/GCS IAM requires a dedicated processing identity;
- Databricks/Delta Lake experiments are local rather than a deployed Databricks workspace;
- Snowflake knowledge is currently conceptual rather than a deployed Snowflake implementation.

These limitations are intentionally documented to distinguish implemented features from target architecture.

## 31. Operational principles

The platform follows these principles:

```text
RAW is immutable.

Every execution is traceable with a run_id.

A retry is not automatically idempotent.

A FAILED Quality Gate must stop the pipeline.

Monitoring must persist before the pipeline is stopped.

Technical failures and Data Quality failures must be distinguishable.

Recovery should restart from the last valid persisted stage.

Secrets must stay outside source code.

DEV and PROD configuration must remain separated.

Observability is part of the pipeline architecture,
not an afterthought.
```

## 33. Summary

The Toulouse Aviation Data Platform demonstrates that a Data Engineering pipeline is not complete when data merely moves from one system to another.

A production-oriented pipeline must also be:

```text
observable
testable
idempotent
recoverable
configurable
traceable
secure
```

The combination of Airflow orchestration, PySpark processing, automated Data Quality gates, `run_id` correlation, monitoring artifacts, alerting, CI/CD and Infrastructure as Code provides the operational foundations required to move from a development pipeline toward a production-grade architecture.
